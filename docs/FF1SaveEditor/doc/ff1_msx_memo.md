# MSX版 ファイナルファンタジー 情報解析メモ

本ドキュメントはゲームディスクのディスクイメージ（DSKファイル）から、ファイルを取り出した前提で記述しています。

## MSX版用ツール

### SayDosTool

ゲームディスクのディスクイメージ（DSKファイル）から、ファイルを取り出したり、格納したりするツールです。

MSX版ファイナルファンタジーはブート時のメッセージによればSayDosというファイル管理システムを使用しており独自のディレクトリエントリが存在します。
ゲーム中では1ByteのIDでファイルを管理しており、管理数は最大255個と思われます。

また、バトル用敵キャラクタ画像は、セクタ直接アクセスを行っています。
（合計ファイル数が255個を超えるための措置と思われます）

`SayDosTool.py`は、ファイルリスト作成、ファイル一括書き出し、ファイル一括書き込みなどを行うことができます。

- ツール：[SayDosTool.py](../SayDosTool.py)
- 仕様調査まとめ：[doc/SayDosTool_specification.md](SayDosTool_specification.md)

各機能の詳細は `-h` オプションでヘルプを表示してください。

### FFPicTool

SayDosToolで取り出したファイルの中には、拡張子がPICのファイルが含まれています。

PICファイルはRLE圧縮された画像ファイルです。

`FFPicTool.py`は、このPICファイルを展開・圧縮することができます。

- ツール：[FFPicTool.py](../FFPicTool.py)
- 仕様調査まとめ：[FFPicTool_specification.md](FFPicTool_specification.md)

各機能の詳細は `-h` オプションでヘルプを表示してください。

#### PICファイル内部レイアウト補足（MAIN.COM: 0x5408 解析より）

- `+0x00` - `+0x09`（10 Byte）: 画像ヘッダ情報
  - `+0x00`: ライン幅モードフラグ（7未満で1ライン128 Byte、7以上で256 Byte）
  - `+0x02` - `+0x03`: 転送先X座標（`DX`）
  - `+0x04` - `+0x05`: 転送先Y座標（`DY`）
  - `+0x06` - `+0x07`: 転送幅（`NX`）
  - `+0x08` - `+0x09`: 転送高さ（`NY`）
- `+0x10` - `+0x2F`（32 Byte）: V9938用16色パレットデータ（1色あたり2 Byte）
- `+0x30` 以降: RLE圧縮された画像データ本体

### FFSprPreview

SayDosToolで取り出したファイルの中には拡張子SPRのファイルが含まれます。

SPRファイルはモード2用16x16スプライトのデータです。

また、BDATA.TBLの末尾にもSPRファイル相当のデータが埋め込まれています。

`FFSprPreview.html`はこのスプライトデータを表示閲覧できます。

画像の書き出しにも対応しています。

- ツール：[FFSprPreview.html](../FFSprPreview.html)

使用されるカラーパレットはマップとバトルで異なるため、
`*.SPR`と `BDATA.TBL`ではそれぞれのパレットへ自動的に切り替えます。

### ファイルIDを使用したセクタアクセス

ゲーム中ではファイル名でアクセスするのではなく、ファイルIDでアクセスしています。

```asm
; in:   A=ファイルID
; out:  DE=開始セクタ
;       HL=終了セクタ

.X5BF5: 
 PUSH   AF              ;5BF5: F5
 PUSH   HL              ;5BF6: E5
 PUSH   IX              ;5BF7: DD E5
 LD     L,A             ;5BF9: 6F
 LD     H,#00           ;5BFA: 26 00
 ADD    HL,HL           ;5BFC: 29
 ADD    HL,HL           ;5BFD: 29
 EX     DE,HL           ;5BFE: EB
 LD     IX,#CA00        ;5BFF: DD 21 00 CA
 ADD    IX,DE           ;5C03: DD 19
 LD     E,(IX+#00)      ;5C05: DD 5E 00
 LD     D,(IX+#01)      ;5C08: DD 56 01
 LD     L,(IX+#02)      ;5C0B: DD 6E 02
 LD     H,(IX+#03)      ;5C0E: DD 66 03
 OR     A               ;5C11: B7
 SBC    HL,DE           ;5C12: ED 52
 INC    L               ;5C14: 2C
 LD     B,L             ;5C15: 45
 POP    IX              ;5C16: DD E1
 POP    HL              ;5C18: E1
 POP    AF              ;5C19: F1
 RET                    ;5C1A: C9
```

- 0xCA00 - 0xCDFF

  ファイルIDごとの開始・終了セクタテーブル。
  
  256 * 2 * 2 Byte = 合計 1,024 Byte

  DSKイメージ上には一致するデータは存在せず、
  BOOT時にディレクトリエントリを走査して
  動的に生成される模様。

- `0x5C1B`: セクタ直接読み込みルーチン（`DE`=開始セクタ, `B`=セクタ数, `HL`=ロード先RAMアドレス）。内部で `0x5D65` を呼び出します。
- `0x5D34` - `0x5DA1`: ディスクI/O実行および `H_TIMI` 割り込み保護処理。セクタ読み書き前に `0xFD9F`（`H_TIMI`）を退避（`0xDC26`）してシステム側フック（`0xDC21`）へ戻し、完了後にゲーム側のフックを復元します。エラー発生時（`0x5DA2`）はエラーコード2未満であればディスク入れ替え・ライトプロテクトメッセージ表示（`0x6509`）へ分岐します。

## VRAM構造と画面制御（MAIN.COM / SMAP.COM / BATTLE.COM）

MSX2版ファイナルファンタジーは、VDPとしてヤマハV9938を採用し、VRAM容量128KByteの構成を前提として動作しています。画面モードは主に **SCREEN 5（グラフィックモード4: 256×212ドット、16色パレット、1ピクセルあたり4bit）** を使用しています。
1Byteあたり横2ドット、横1ライン（256ドット）は128Byteで構成されます。VDPの座標系では X: 0 - 255、Y: 0 - 1023 の仮想空間として管理され、256ライン単位で計4ページ（各32KByte）に分割されています。

### 1. VRAM 128KByte メモリマップ概要

| ページ番号 | VRAMアドレス範囲      | Y座標範囲  | 主な役割・用途                                                       |
| :--------- | :-------------------- | :--------- | :------------------------------------------------------------------- |
| ページ0    | `0x00000` - `0x07FFF` | 0 - 255    | **表示／描画プレーン0**（表画面／裏画面のダブルバッファ片側）        |
| ページ1    | `0x08000` - `0x0FFFF` | 256 - 511  | **表示／描画プレーン1**（表画面／裏画面のダブルバッファ片側）        |
| ページ2    | `0x10000` - `0x17FFF` | 512 - 767  | **オフスクリーン作業領域**（ウィンドウ描画バッファ、フォント展開等） |
| ページ3    | `0x18000` - `0x1FFFF` | 768 - 1023 | **グラフィック素材キャッシュ**（マップチップ、敵画像、キャラ素材等） |

### 2. ページフリップ（ダブルバッファリング）制御

フィールド歩行スクロール時や戦闘画面の更新時、MSX版では画面の書き換えチラツキ（テアリング）を防止するため、ページ0とページ1を用いたダブルバッファリングが行われます。

- システムワーク `0xDC1B`（VRAM表示プレーンフリップフラグ）が現在の表示状態を保持します。
  - `0x00`: ページ0（Y=0〜211）を表示中。描画処理は裏画面であるページ1（Y=256〜467）に対して実行。
  - `0xFF`: ページ1（Y=256〜467）を表示中。描画処理は裏画面であるページ0（Y=0〜211）に対して実行。
- 描画完了後、`MAIN.COM` の `FLIP_PLN`（`0x5AD1`）サブルーチンが呼び出され、VSYNC割り込み同期（`0xDC1D` 監視）でVDPレジスタ2（表示開始アドレス）を書き換えることで、画面プレーンをフリップします。

### 3. 各モジュールにおけるVRAM利用形態

#### ① MAIN.COM（ワールドマップ・フィールド統括時）

- **ページ0／ページ1**: フィールド表示画面（Y: 0 - 211 / Y: 256 - 467）。スクロール処理時に裏画面側へ新規タイル列・行を順次転送します。
- **ページ2（Y: 512 - 767）**:
  - `FONT.PIC`、`FONT2.PIC`（各4,096 Byte）の展開領域（`Y = 0x2C8` 以降、32文字/行）。
  - 会話テキストウィンドウ枠やステータス枠の構築領域。
- **ページ3（Y: 768 - 1023）**:
  - `MAINBG.PIC`（ワールドマップ用8×8キャラクタ群、8,192 Byte）を展開。
  - `JOBS_L1.PIC` または `JOBS_L2.PIC`（プレイヤー歩行グラフィック、各クラス4方向×2パターン）を展開。
  - 8×8ドットのBGキャラクタ群は、VDPの高速矩形転送コマンド（HMMM）の転送元（SX, SY）として直接参照されます。

#### ② SMAP.COM（サブマップ・街・ダンジョン・施設時）

- **ページ0／ページ1**: 街やダンジョンの表示画面。
- **ページ2（Y: 512 - 767）**:
  - ショップ施設（武器屋、防具屋、道具屋、魔法屋、宿屋、教会）のメニューウィンドウ、商品リスト、所持金表示枠を一時構築（例: DX=`0x0058`, DY=`0x0228` 等）。
  - 会話メッセージウィンドウの描画バッファ。
- **ページ3（Y: 768 - 1023）**:
  - `SUB0BG.PIC` - `SUB7BG.PIC`（現在マップのタイルセットに対応する8×8キャラクタ群、4,096 Byte）を展開。
  - `SHOPBG.PIC`（ショップ施設の内装・カウンター素材、3,584 Byte）を展開。
  - スプライトアトリビュートテーブル（SAT）およびスプライトカラーテーブル（SCT）は、VRAM上位アドレスに配置され、毎フレームNPC座標が更新されます。

#### ③ BATTLE.COM（戦闘画面時）

- **ページ0／ページ1**: 戦闘メイン画面。上部が戦闘背景・敵・味方描画エリア（Y: 0 - 159）、下部がステータス・コマンド入力エリア（Y: 160 - 211）。
- **ページ2（Y: 512 - 767）**:
  - 戦闘コマンドメニュー、魔法・アイテム一覧ウィンドウの一時展開（`DY = 0x0200` に対し `HMMV` でクリア後、枠線と文字を描画）。
  - 味方バトルキャラクタ素材（`BAT_L1.PIC` / `BAT_L2.PIC`、各8,192 Byte）の展開。
- **ページ3（Y: 768 - 1023）**:
  - 戦闘背景チップ（`LAND.PIC`、6,144 Byte）を展開（`0x8B0C`）。
  - 敵モンスター画像（`ENEMY_???.PIC`）をセクタ直接読み込みルーチン（`0x8F56`）で読み込み、PIC展開ルーチン経由で Y: 768 以降の領域へ一時展開。
  - 戦闘エフェクト用グラフィック素材を展開。

### 4. スプライトプレーンの管理（スプライトモード2）

- MSX2のスプライトモード2を使用し、16×16ドットのスプライトを表示します。
- スプライト属性テーブル（SAT）およびスプライトジェネレータテーブル（SGT）は、VRAMの特定アドレス（通常 `0x7600` 付近）に配置されます。
  - `MAIN.COM` のスプライト転送処理（`0x52F0`〜`0x53F0`）では、128 KByte VRAM空間上で以下のアドレスに配置されます。
    - **SCT（スプライトカラーテーブル）**: `0x17800`（ページ2内 `0x7800`）
    - **SAT（スプライトアトリビュートテーブル）**: `0x17A00`（ページ2内 `0x7A00`）
    - **SGT（スプライトジェネレータテーブル）**: `0x1F800`（ページ3内 `0xF800`）
- プレイヤーやNPC、乗り物、エフェクトは、3枚のスプライトを同座標に重ねて表示することで、4色（透明＋3色）の多色キャラクタを表現しています。

### 5. MAIN.COM のモジュール連携と VDP コマンド／フェード処理

`MAIN.COM`（RAM `0x4000` ロード、`0x4000` 開始）は、各オーバーレイモジュールを RAM `0x8000` へ切り替えロードして統括します。

- **モジュール呼び出し構成**:
  - **起動時（`0x4006`）**: `STARTUP.COM`（ID `0x09`）を `0x8000` にロードして実行し、タイトル・パーティ作成等を行います。
  - **フィールドAボタン（`0x406D`）**: ワールドマップ中（`0xC230 == 0`）に決定キー（`0xDC1A == 0x20`）を押すと、`0x8000`（`SMAP.COM`）を実行します。
  - **メニュー（`0x407F`）**: F1キー（`0xDC1A == 0xF1`）で `SP` を `0xC224` へ退避し、`MENU.COM`（ID `0x07`）を `0x8000` へロードして実行します。終了後、サブマップ中なら `SMAP.COM`（ID `0x06`）を再ロードします。
  - **セーブ／テント等（`0x4121`）**: F2キー（`0xDC1A == 0xF2`）かつワールドマップ中に `SMAP.COM` をロードし `0x8006` を呼び出します。
  - **強制イベント（`0x416C`）**: `0xDC44 != 0` かつワールドマップ中に `SMAP.COM` の `0x8009` を呼び出します。
  - **世界地図表示（`0x4206`）**: ワールドマップ中に特定キー入力があると `MAPDSP.COM`（ID `0x0A`）を `0x8000` へロードして実行します。
  - **橋開通デモ／エンディング（`0x428D`, `0x43F5`）**: `OPENEND.COM`（ID `0x0B`）には2つのエントリがあり、橋到達時（`0xC236 == 0` かつ橋座標一致）は `0x8000`、ラスボス戦（`BATSCENE ID = 0x7B`）勝利後の復帰時は `0x8003` を呼び出します。
- **VDPコマンドラッパー群（`0x7025` - `0x716F`）**:
  - `0x7025`: `HMMM`（高速矩形VRAM間転送、CMD `0xD0`）
  - `0x7030`: `LMMM`（論理演算付き矩形転送、CMD `0x90` | `0xDC15`）
  - `0x7085`: `HMMV`（高速矩形塗りつぶし、CMD `0xC0`）
  - `0x708E`: `LMMV`（論理演算付き矩形塗りつぶし、CMD `0x80` | `0xDC15`）
  - `0x7099`: `LINE`（直線描画、CMD `0x70` | `0xDC15`）
- **パレットバッファとフェード処理（`0x7256` - `0x73F7`）**:
  - `0x72A0` - `0x72CF`（48 Byte）および `0x72D0` - `0x72FF`（48 Byte）に現在パレット・目標パレットのRGB値を保持し、`0x7300`（フェードアウト）および `0x73A0`（フェードイン）で8段階（0〜7）のフェード制御を行います。
- **初期化および戦闘呼び出し・復帰処理（`0x4048` - `0x406C` / `0x43EA` - `0x4425`）**:
  - **ゲーム開始・コンティニュー直後（`0x4048` - `0x406C`）**: `0x4011` から呼び出される初期化ルーチンであり、末尾の `0x4069: CALL 0x5591` / `0x406C: RET` を抜けて本編へ移行します。
  - **戦闘呼び出し・復帰処理（`0x43EA` - `0x4425`）**: `0x43EA` で `BATTLE.COM`（ID `0x08`）をロードして `CALL 0x8000` を実行します（ラスボス戦 `0xDC31 == 0x7B` のエンディング分岐を含む全戦闘がここを経由します）。終了後は `0x4422: CALL 0x4E9C` を経て `0x4425: RET` でメインループへ復帰します。
- **末尾のワークおよび空き領域（`0x7FA4` - `0x7FFF`）**:
  - `0x7FA4` - `0x7FA8`: OPLL（MSX-MUSIC）検出時のワーク領域として使用されます（なお `0x7FF6` へのアクセスはカートリッジスロット上のレジスタに対する `WRSLT` であり、メインRAMへの書き込みではありません）。
  - `0x7FA9` - `0x7FFF`（87 Byte）: コード・データともに未参照の `0x00` 領域です。

## EXDATA1.COM / EXDATA2.COM の仕様とデータ構造

ファイル名に `.COM` の拡張子が付与されていますが、実行プログラムではなく、**全サブマップ（街・城・ダンジョン）のNPC初期配置・属性テーブル** が格納された固定長レコード形式のデータファイルです。

### 1. ファイルの分割とマップ割り当て

全61種類のサブマップ（`SUB00.MAP`〜`SUB3C.MAP`）に対応するため、データは2ファイルに分割されて格納されています。進入先マップIDに応じて、メインRAM `0x1000` へロードされます。

| ファイル名    | ファイルID | サイズ     | 収録対象マップID       | 格納マップ数 | 備考                                            |
| :------------ | :--------: | :--------- | :--------------------- | :----------: | :---------------------------------------------- |
| `EXDATA1.COM` | 0xD8 (216) | 8,192 Byte | マップ `0x00` - `0x1F` |  32マップ分  | コーネリア、各町、アースの洞窟、グルグ火山B1F等 |
| `EXDATA2.COM` | 0xD9 (217) | 8,192 Byte | マップ `0x20` - `0x3C` |  29マップ分  | グルグ火山B2F以降、海底神殿、浮遊城、過去神殿等 |

- 各サブマップごとに **256 Byte（0x0100 Byte）** の固定領域が割り振られています（32ブロック × 256 Byte = 8,192 Byte）。
- `EXDATA2.COM` において、実際のゲームマップ（0x3C: 巨人の洞窟 東まで）を超えた領域（0x3D〜0x3F）は 00 パディングされています。

#### 【EXDATA2.COM（0x0000 - 0x1FFF: マップ 0x20 - 0x3C）】

- `0x0000`: マップ 0x20（バハムートの洞窟 B2 / 竜王の部屋）
- `0x0400`: マップ 0x24（滝の裏の洞窟 / ロボット）
- `0x0E00`: マップ 0x2E（海底神殿 / 人魚）
- `0x1000`: マップ 0x30（浮遊城 1F）
- `0x1C00`: マップ 0x3C（巨人の洞窟 東）
- その他のNPCが存在しない階層（ダンジョン通路フロア等）は、ブロック全体が `0x00` で埋められています。

### 3. 1マップあたりのブロック構成（256 Byte）

1つのサブマップブロック（256 Byte）内には、**最大16体分のNPC初期データ（1体あたり16 Byte）** が格納されています。

```text
+0x000: NPC #0  初期データ (16 Byte)
+0x010: NPC #1  初期データ (16 Byte)
+0x020: NPC #2  初期データ (16 Byte)
  :
+0x0F0: NPC #15 初期データ (16 Byte)
```

NPCの配置数が16体未満のマップでは、未使用スロットの先頭Byte（グラフィックID）が `0x00` となり、残りの領域は `0x00` で埋められています。

### 4. NPC初期データレコード構造詳細定義（1体あたり16 Byte）

`SMAP.COM` のNPC移動ルーチン（`0x86D6` - `0x88D2`）およびダンプデータの解析結果に基づくレコード定義です。

| オフセット | サイズ | フィールド名             | 格納値および機能説明                                                                               |
| :--------- | :----- | :----------------------- | :------------------------------------------------------------------------------------------------- |
| `+0x00`    | 1 Byte | **グラフィックID**       | `EXTRA.SPR` 内のスプライトパターン番号。`0x00` の場合は未登録スロット（非表示）。                  |
| `+0x01`    | 1 Byte | **移動状態フラグ**       | `0x00`: 静止状態、`0x01`: 移動処理中。初期値は `0x00`。                                            |
| `+0x02`    | 1 Byte | **内部ピクセルX座標**    | サブマップ内X座標（8ドット＝半タイル単位）。初期値はタイル座標X（`+0x0A`）の2倍値（`TileX * 2`）。 |
| `+0x03`    | 1 Byte | **内部ピクセルY座標**    | サブマップ内Y座標（8ドット＝半タイル単位）。初期値はタイル座標Y（`+0x0B`）の2倍値（`TileY * 2`）。 |
| `+0x04`    | 1 Byte | **現在の向き**           | `0x00`: 上、`0x01`: 右、`0x02`: 下、`0x03`: 左。初期値は通常 `0x02`（正面・下向き）。              |

| `+0x07`    | 1 Byte | **移動AIタイプ**         | `0x00`: 移動不可（定位置で静止）、`0x01`: ランダム移動（周期ごとに4方向判定）。                    |

| `+0x0D`    | 1 Byte | **退避Y座標 / 予備**     | 会話・イベント時の座標退避領域。初期値は `0x00`。                                                  |
| `+0x0E`    | 1 Byte | **未使用パディング**     | 常に `0x00`。                                                                                      |
| `+0x0F`    | 1 Byte | **未使用パディング**     | 常に `0x00`。                                                                                      |

### 5. 実データによる構造の検証

#### ① ガイアの街（`EXDATA1.COM` オフセット `0x0500`）

```text
000500 13 00 62 26 02 14 00 01 00 0A 31 13 00 00 00 00
```

- **グラフィックID (`+0x00`)**: `0x13`（町人グラフィック）
- **タイル座標 (`+0x0A`, `+0x0B`)**: X=`0x31`（49タイル）、Y=`0x13`（19タイル）
- **内部ピクセル座標 (`+0x02`, `+0x03`)**:
  - X = 49 × 2 = 98 (`0x62`)
  - Y = 19 × 2 = 38 (`0x26`)
  タイル座標の2倍（8ドット単位）と一致しています。
- **向き (`+0x04`)**: `0x02`（下向き）
- **移動AI (`+0x07`)**: `0x01`（街中をランダム移動）
- **フラグ番号 (`+0x09`)**: `0x0A`（進行フラグと連動）

#### ② 巨人の洞窟 東（`EXDATA2.COM` オフセット `0x1C00`）

```text
001C00 14 00 10 0E 02 1C 00 01 00 0B 08 07 00 00 00 00
```

- **グラフィックID (`+0x00`)**: `0x14`（巨人グラフィック）
- **タイル座標 (`+0x0A`, `+0x0B`)**: X=`0x08`（8タイル）、Y=`0x07`（7タイル）
- **内部ピクセル座標 (`+0x02`, `+0x03`)**:
  - X = 8 × 2 = 16 (`0x10`)
  - Y = 7 × 2 = 14 (`0x0E`)
- **向き (`+0x04`)**: `0x02`（下向き）
- **移動AI (`+0x07`)**: `0x01`
- **フラグ番号 (`+0x09`)**: `0x0B`（「スタールビー」を渡すイベントの進行フラグと連動）
- エントリ2以降（`0x1C10`〜）はすべて `0x00` であり、洞窟内に巨人が1体のみ配置されている状態を表しています。

### 6. NPC会話分岐処理との連携

`SMAP.COM` の会話処理（`0x88D8`: `NPC_TALK`）では、接触したNPCのグラフィックID（`+0x00`）をキーとして `0x88F5` のジャンプテーブルを参照します。
町人や固有NPC（王様、マトーヤ、巨人等）ごとに分岐し、進行フラグ（`+0x09`）の状態に応じて表示するメッセージ番号（`MESSAGE.MSG` 内のテキスト）が選定されます。

### 7. SMAP.COM による読み込みと展開シーケンス

サブマップ進入時、`MAIN.COM` および `SMAP.COM` は以下の手順でデータを展開します。

1. **ファイル判定**:
   - 進入先マップIDが `0x00` - `0x1F` の場合は `EXDATA1.COM`（ファイルID: `0xD8`）を選択。
   - マップIDが `0x20` - `0x3C` の場合は `EXDATA2.COM`（ファイルID: `0xD9`）を選択。
2. **一時バッファへのロード**:
   - 選択されたファイルをメインRAM `0x1000` へロードします。
3. **NPC管理バッファへの転送**:
   - `(マップID & 0x1F) × 0x100` でファイル内オフセットを算出し、該当マップの256 Byte（16体分）をメインRAM `0xC400` - `0xC4FF`（NPC状態管理バッファ）へ転送します。
4. **マップデータのロード（上書き）**:
   - 続いて対象マップファイル（`SUBxx.MAP`）を同じく `0x1000` へ読み込み、マップを展開します（一時バッファは上書きされますが、`0xC400` のNPCデータは保持されます）。

## マップ表示処理の詳細

### 1. ワールドマップ描画処理（MAIN.COM）

ワールドマップは256×256タイルの領域であり、全データをメインRAMに展開することは不可能です。そのため、行単位のオンデマンド伸長とVRAMダブルバッファを組み合わせたスクロール描画が行われます。

```text
[プレイヤー移動入力]
        │
        ▼
[0x46DA: MOVE_CTL] 移動方向判定・足元属性チェック
        │
        ├─ 障害物なし ───┐
        ▼                 ▼
[0x58CC: DRAW_1TL]     [0x5A86: DRAW_HAF]
新境界タイルの裏画面描画   4ドット単位の補間スクロール
        │                 │
        └────────┬────────┘
                 ▼
        [0x5AD1: FLIP_PLN] VSYNC同期で表示プレーン切替
```

- **行先頭参照とRLE解凍**:
  - `MMAP.VEC`（ファイルID: `0x78`、512 Byte）に格納されている各行（全256行）の先頭ポインタを参照します。ポインタ値から `0x8200` を引いたオフセットで `MAIN.MAP` 内を参照し、該当行のランレングス圧縮データを解凍してラインバッファ（256 Byte）へ展開します。
  - 圧縮形式はサブマップと同様のRLE方式（最上位bitが1なら下位7bitがタイルIDで直後が連続数、最上位bitが0なら単一タイルID）であり、横1行（256タイル）ごとに独立して圧縮されています。
  - 行をまたぐ依存関係がないため、縦スクロール時に露出する新規行のみをオンデマンドで高速に解凍できます。
- **タイルセット定義の参照と合成**:
  - タイルID（0x00〜0x7F）に基づき、タイル定義テーブル（メインRAM `0xC500` - `0xC7FF`、`MAIN.CHR`）から対応する4枚の8×8チップ番号（左上・右上・左下・右下）を取得します。
  - タイル属性テーブルには、通行可否、海、山、森、ダメージ床、扉、宝箱、階段・ワープなどの物理判定フラグが保持されます。
- **VDP HMMMコマンドによる転送**:
  - VRAMページ3に展開されている `MAINBG.PIC` から、該当する8×8チップを指定座標（SX, SY）から読み出し、裏画面プレーン（DX, DY）へHMMMコマンドで転送して16×16ドットタイルを構成します。
- **スムーズスクロールとプレーンフリップ**:
  - 画面解像度は 256×212ドット であり、画面上には常時 横16タイル×縦13〜14タイル が表示されます。
  - 1タイルの移動（16ドット）を一度に行うのではなく、4ドット刻みの中間フレーム処理（`DRAW_HAF`: `0x5A86`）を実行します。
  - 移動方向の前方に新しく露出するマップ領域（横16タイルの行、または縦14タイルの列）を計算し、端行・端列の追加描画（`DRAW_1TL`: `0x58CC`）で裏画面プレーンへ転送します。
  - 描画完了後、`FLIP_PLN`（`0x5AD1`）を呼び出し、VSYNC同期で画面プレーンを切り替えます。
- **乗り物スプライト表示**:
  - 船・カヌー・飛空艇搭乗時は、プレイヤーの歩行スプライトに代わり `MSPR.SPR` のグラフィックが選択されます。
  - 飛空艇搭乗時は、本体スプライトを数ピクセル上方に浮かせて描画し、直下の地上タイル位置に影スプライトを表示することで高度感を表現します。
- **毒ダメージおよびイベントタイル判定（MAIN.COM: 0x41C0, 0x4752）**:
  - 1歩移動完了時（`0xDC2E != 0`）、毒状態（状態異常 `+0x01` の bit 2）で生存中のキャラクタは現在HPが1減少します（最小値1までで0にはなりません）。また飛空艇搭乗時（`0xC237 == 3`）を除き、足音SE（`0x06`）を再生します。
  - 移動成立時のタイル判定（`0x4752`）では、タイル定義上位属性（`0xC23D` の上位ビット `0x1E`）に応じて、宝箱/イベント（`0x01`）、扉（`0x02`、カギ判定）、ダメージ床（`0x03`）、回復パネル（`0x06`）、クリスタル台座点灯（`0x07` - `0x09`）、強制イベント（`0x0C` - `0x0F`）が分岐します。

### 2. サブマップ描画処理（MAIN.COM / SMAP.COM）

サブマップ（64×64タイル = 4,096タイル）は、街やダンジョン進入時にマップ全体が解凍展開されます。

- **マップデータの全展開とRLE圧縮フォーマット仕様**:
  - `SUBxx.MAP`（可変長ランレングス形式）が読み込まれ、マップ左上（0, 0）から右下（63, 63）へ向かって順次展開されます。

```text
[ストリーム先頭]
       │
       ├─ 最上位bit = 1 (0x80 - 0xFF) : ランレングス指定
       │     ├─ タイルID = (バイト値 & 0x7F)
       │     └─ 直後のバイト = 連続数
       │
       └─ 最上位bit = 0 (0x00 - 0x7F) : 単一タイルID
             └─ そのタイルIDを1個直接出力
```

例（`SMAP05.MAP` ガイアの街 先頭データ）:

```text
80 47        -> タイル 0x00 (0x80 & 0x7F) が 71個 (0x47)（山・森で外周を埋める）
86 0F        -> タイル 0x06 (0x86 & 0x7F) が 15個 (0x0F)（森）
...          -> 連続して街内部の敷地タイルを展開
```

4,096タイル分が出力されるか、終端コードに達した時点で展開を終了します。

- **タイルセットグラフィックの配置と合成**:
  - `POSIT.TBL` の `0x0180`〜 を参照してタイルセットID（0 - 7）を特定し、対応する `SUBxBG.PIC` をVRAMページ3へ、`SUBx.CHR`（タイル構成・属性定義）をRAM `0xC500` - `0xC7FF` へロードします。
  - タイル番号から `0xC500` のテーブルを参照し、4つの8×8キャラクタID（左上, 右上, 左下, 右下）を取得してVRAMページ3から裏画面プレーンへHMMMコマンドで転送します。
- **画面描画**:
  - プレイヤーの現在タイル座標を中心とした周囲16×14タイル分の領域を走査し、裏画面プレーンへ転送します。
- **動的ギミックの書き換え**:
  - **宝箱**: 回収済みフラグがセットされると、マップデータのタイルIDを開箱チップIDへ変更し、`0xDC4D` フラグによりVRAM上の該当箇所を即座に再描画します。
  - **扉**: 接触・開錠時に扉が開いた状態のタイルへ書き換え、進入不可属性を解除します。
  - **ダメージ床**: 移動成立時にタイル属性（`0xC23D`）をチェックし、溶岩等のダメージ床であればパーティ生存者のHPを一定値減算してSEを鳴らします。

### 3. サブマップ内NPCスプライト描画処理（SMAP.COM: 0x80DE）

サブマップ内を徘徊・静止するNPCは、背景BGではなくスプライトプレーンを用いて描画されます。

- **走査とカリング（描画範囲判定）**:
  - `DRAW_NPC`（`0x80DE`）にて、`0xC400` - `0xC4FF` のNPCバッファ（16体分）を毎フレーム走査します。
  - グラフィックID（`+0x00`）が `0x00` のスロットは未登録としてスキップします。
  - 各NPCのサブマップ内内部座標（`+0x02`, `+0x03`）から現在のカメラ原点座標（画面左上基準）を減算し、画面内ローカル座標（X, Y）を算出します。
  - 画面外（Y < 0 または Y >= 212、X < 0 または X >= 256）のNPCには、スプライトアトリビュートテーブル（SAT）のY座標に `0xD8`（非表示フラグ）を設定して除外します。
- **スプライト属性テーブル（SAT）の構築**:
  - 画面内NPCについて、向き（`+0x04`: 0=上, 1=右, 2=下, 3=左）と足踏みパターン（`+0x05`）から、`EXTRA.SPR` 内の対応パターン番号を算出します。
  - 1体のNPCにつき、スプライト3枚分のパターン番号、表示座標（X, Y）、およびラインカラーテーブルを設定し、スプライトを重ねて表示することで多色表示を実現します。

### MENU.COM の能力値再計算処理とメモリ構成

`MENU.COM`（RAM `0x8000` ロード、11,776 Byte）では、武器・防具メニューの終了時にキャラクタブロック内の素パラメータ（`+0x28` - `+0x2A`）を参照し、必ず各能力値を再計算します（`0x8D1F` 周辺）。

- **攻撃力再計算（`0x8D59` - `0x8D62`）**: 装備武器の合計攻撃力（ワーク `0x8D44`）に `(IX+0x28)`（`ちから / 2`）を加算し、`(IX+0x20)` へ格納します。
- **命中率再計算（`0x8D63` 周辺）**: 装備武器の合計命中率に `(IX+0x29)`（素の命中率）を加算し、`(IX+0x21)` へ格納します。
- **防御力再計算（`0x8D95` - `0x8D9B`）**: 装備防具の合計防御力（ワーク `0x8D44`）を `(IX+0x22)` へ格納します。
- **回避率再計算（`0x8D9C` / `0x8DB4` 周辺）**: `(IX+0x2A)`（素の回避率）から装備防具の合計重さを減算し、`(IX+0x23)` へ格納します。
- **素手・無防具時のモンク補正**: 原作の MSX2 版にはモンク／スーパーモンク用の特別な攻撃力・防御力補正が存在しないため、武器や防具を外した状態でも通常ジョブと同様に `(IX+0x28)` および `0` として計算されます。
- **武器データテーブル参照（`0x8E45`）**: 武器性能の参照・計算時に使用されます。
- **末尾空き領域**: ファイル末尾に 73 Byte の `0x00` パディング領域が存在します。

## マップ

### VEC ファイル : 圧縮マップの各ライン先頭へのポインタテーブル

- `MMAP.VEC`

  ワールドマップのライン先頭ポインタ(16bit)のテーブル。

  ファミコン版の0x4000 (NESファイル 0x4010)と同一。
  
  ファミコンでの実行時アドレスで書かれており、
  0x8000が圧縮データ先頭という前提で書かれています。

### MAPファイル : マップデータ本体

- `MAIN.MAP`

  ワールドマップの本体データ。
  
  フィールドサイズは256×256タイル。
  
  行ごとに独立してランレングス圧縮されており、
  各行の先頭アドレスはポインタテーブル（`MMAP.VEC`）を参照します。
  `MMAP.VEC` に書かれた値から `0x8200` を引いた値をファイル内オフセット値とします。

  - **行単位RLE圧縮フォーマット**:

  ```text
  [ストリーム先頭（行先頭ポインタ位置）]
         │
         ├─ 最上位bit = 1 (0x80 - 0xFF) : ランレングス指定
         │     ├─ タイルID = (バイト値 & 0x7F)
         │     └─ 直後のバイト = 連続数
         │
         └─ 最上位bit = 0 (0x00 - 0x7F) : 単一タイルID
               └─ そのタイルIDを1個直接出力
  ```

  展開出力が256タイルに達した時点で1行の解凍を終了します。

  - 参考：ファミコン版

    - 0x4200 (NESファイル 0x4210) に置かれているデータ。
    - ライン先頭ポインタテーブルの値から0x4000を引いたROMアドレスを参照します。
      (NESファイルの場合は、0x3FF0)

- `SUB00.MAP` - `SUB3C.MAP`

  通常マップの本体データ。

  64×64（4,096タイル）のサブマップデータは、容量削減のためランレングス形式の可変長圧縮で格納されています。マップの左上（0, 0）から右下（63, 63）に向かって順に展開されます。

  ```text
  [ストリーム先頭]
         │
         ├─ 最上位bit = 1 (0x80 - 0xFF) : ランレングス指定
         │     ├─ タイルID = (バイト値 & 0x7F)
         │     └─ 直後のバイト = 連続数
         │
         └─ 最上位bit = 0 (0x00 - 0x7F) : 単一タイルID
               └─ そのタイルIDを1個直接出力
  ```

  例（`SUB05.MAP` ガイアの街 先頭データ）:

  ```text
  80 47        -> タイル 0x00 (0x80 & 0x7F) が 71個 (0x47)（山・森で外周を埋める）
  86 0F        -> タイル 0x06 (0x86 & 0x7F) が 15個 (0x0F)（森）
  ...          -> 連続して街内部の敷地タイルを展開
  ```

  - 終端: 4,096タイル分が出力されるか、終了マーカーが出現すると展開を終了。

### CHR ファイル ： マップ用タイルセット定義

各マップ毎の
**タイル属性** + **タイルセット定義（キャラクタの組み合わせ）**
が格納されたファイル。

内容はファミコン版と同じ。
ただし、MSX版にはパレット割り当てテーブルは存在しない。

- `MAIN.CHR`

  ワールドマップ用タイル定義データ。
  
  ファミコン版の 0x0000（NESファイル 0x0010） と同一。
  - `+0x0000` - `+0x00FF`（DSK `0x067A00`〜、RAM `0xC500` - `0xC5FF`）: タイル属性テーブル（128タイル × 2 Byte = 256 Byte）
  - `+0x0100` - `+0x02FF`（DSK `0x067B00`〜、RAM `0xC600` - `0xC7FF`）: タイルチップ定義（128タイル × 4プレーン［左上, 右上, 左下, 右下］各128 Byte = 512 Byte）

- `SUB0.CHR` - `SUB7.CHR`
  
  通常マップ タイルセット0 - 7 の タイル定義データ。

  ファミコン版と同一。

### マップ用 PIC ファイル : 画像ファイル

- `MAINBG.PIC`

  ワールドマップ用タイルセット用 マップチップ（8x8キャラクタ）
  並びはファミコン版と同一。

- `SUB0BG.PIC` - `SUB7BG.PIC`

  通常マップタイルセット0 - 7 用 マップチップ（8x8キャラクタ）
  並びはファミコン版と同一。

### SPR ファイル ： スプライトデータ

#### スプライト最小単位

16x16 スプライトパターン 計32Byte + ラインカラーデータ 計8Byte  
= 合計 40Byteで1つのスプライトを構成。

- スプライトパターンは8x16が横に2つ並んで16x16ピクセルを表現している。
- ラインカラーは偶数行が上位4ビット、奇数行が下位4ビットにpackされている。

#### キャラクタ最小単位

スプライト3枚単位。

3枚のスプライトを重ねて表示することで1キャラクタを多色表現している。

CCビットは使用しておらずカラーコードのORは使わず、重ね合わせ表示を行っている。

#### ファイルの内容

- `MSPR.SPR`

  フィールドで表示するスプライト。  

  - 船、飛空艇、カヌー、影、橋、海峡の並び。  
  - 船、飛空艇、カヌーは2パターンアニメ×4方向（上右下左）の8パターンずつ。
  - ファイル内およびDSK上の個別アドレス（1キャラクタ = 3枚重ね = 120 Byte）:
    - **船**: ファイル内 `0x0000` - `0x03BF` / DSK `0x082800` - `0x082BBF`（4方向 × 2パターン = 8個: 960 Byte）
    - **飛空艇**: ファイル内 `0x03C0` - `0x077F` / DSK `0x082BC0` - `0x082F7F`（4方向 × 2パターン = 8個: 960 Byte）
    - **カヌー**: ファイル内 `0x0780` - `0x0B3F` / DSK `0x082F80` - `0x08333F`（4方向 × 2パターン = 8個: 960 Byte）
    - **飛空艇の影**: ファイル内 `0x0B40` - `0x0BB7` / DSK `0x083340` - `0x0833B7`（1パターン: 120 Byte）
    - **北の橋**: ファイル内 `0x0BB8` - `0x0C2F` / DSK `0x0833B8` - `0x08342F`（1パターン: 120 Byte）
    - **海峡（運河）**: ファイル内 `0x0C30` - `0x0CA7` / DSK `0x083430` - `0x0834A7`（1パターン: 120 Byte）

  - 参考：ファミコン版  

    - 乗り物は影、橋、海峡、空きの後に配置されている。
    - 乗り物は左右反転機能で反転するので、
      2パターンアニメ×3方向（上下左）の6パターンずつ。
  
    アドレス配置は

    - 影　　： 0x9C00（NESファイルは0x9C10）1個
    - 橋　　： 0x9C40（NESファイルは0x9C50）1個
    - 海峡　： 0x9C80（NESファイルは0x9C90）1個
    - 空き　： 0x9CC0（NESファイルは0x9CD0）1個
    - 船　　： 0x9D00（NESファイルは0x9D10）2*3=6個
    - 飛空艇： 0x9E80（NESファイルは0x9E90）2*3=6個
    - カヌー： 0xA000（NESファイルは0xA010）2*3=6個

  ※ ファミコン版、MSX版ともに、プレイヤーキャラとは上下の並びが異なる。

- `EXTRA.SPR`

  町やダンジョンで表示されるキャラクタ。
  
  1キャラクタあたり4パターン。  
  （上1パターン、下1パターン、左2パターンの計4パターン）
  
  こちらは `MSPR.SPR` と異なり、ファミコン版の並びと一致している。
  
  - 参考：ファミコン版

    0xA200-0xBFFF（NESファイルでは0xA210-0xC0FF）にデータが存在する。
  
- `EXTRA2.SPR`

   パターンデータが存在せずカラーテーブルだけが並ぶ特殊なデータ。

   内容は`EXTRA.SPR` のカラーと同一なので無視して良い。

- `BDATA.TBL`（オフセット 0x1C70-）

  バトル用のスプライトデータ（攻撃・魔法エフェクト等）。
  拡張子はTBLですが、オフセット 0x1C70（DSK 0x7A070）以降に40Byte単位（パターン32Byte＋カラー8Byte）のスプライトデータが格納されている。
  表示にはバトル用パレットを使用します。

## 文字コード・フォント描画仕様（FF1.def / MAIN.COM）

### 1. 文字コード体系（FF1.def）

MSX版ファイナルファンタジーでは、メッセージテキスト（`*.MSG`、システムメッセージ）およびセーブデータのキャラクタ名（4 Byte）で共通の文字コード体系（`0x48` - `0xFF`）を使用します。`0x47` 以下の値はメッセージ表示エンジンの制御コードまたは終端コードとして扱われます。

```text
+48  がぎぐげござじず
+50  ぜぞだぢづでどばびぶべぼガギグゲ
+60  ゴザジズゼゾダヂヅデドバビブベボ
+70  ぱぴぷぺぽパピプペポ／をっゃゅょ
+80  ０１２３４５６７８９あいうえおか
+90  きくけこさしすせそたちつてとなに
+A0  ぬねのはひふへほまみむめもやゆよ
+B0  らりるれろわんァィ。ェォッャュョ
+C0  ゛゜ー‥！？ＬＥＨＰアイウエオカ
+D0  キクケコサシスセソタチツテトナニ
+E0  ヌネノハヒフヘホマミムメモヤユヨ
+F0  ラリルレロワン┏━┓┃│┗─┛　
```

### 2. フォントのVRAM展開配置と濁点・半濁点分離描画（MAIN.COM: 0x67B9 - 0x6914）

`FONT.PIC` / `FONT2.PIC` の文字グラフィックは VRAM ページ2（Y=`0x2C8` 以降）に展開されており、`0x6875` の座標変換ルーチンにより文字コードから VRAM 転送元座標 `(SX, SY)` が計算されます（1行あたり32文字［256ドット］配置、基準コードは `0x60` 以降で `SX = (コード & 0x1F) * 8`、`SY = ((コード - 0x60) / 32) * 8 + 0x2C8`）。

- **濁音・半濁音の変換ロジック（`0x67B9` - `0x67FA`）**:
  - `0x48`〜`0x56`（が〜ぼ）: 清音コード `コード + 0x47` へ変換し、濁点フラグ（`0x6921` = `0x01`）をセット
  - `0x57`〜`0x5B`（ば〜ぼ / 濁点範囲）: 清音コード `コード + 0x4C` へ変換し、濁点フラグをセット
  - `0x5C`〜`0x6A`（ガ〜ド）: 清音コード `コード + 0x73` へ変換し、濁点フラグをセット
  - `0x6B`〜`0x6F`（バ〜ボ）: 清音コード `コード + 0x78` へ変換し、濁点フラグをセット
  - `0x70`〜`0x74`（ぱ〜ぽ）: 清音コード `コード + 0x33` へ変換し、半濁点フラグ（`0x6921` = `0xFF`）をセット
  - `0x75`〜`0x79`（パ〜ポ）: 清音コード `コード + 0x6E` へ変換し、半濁点フラグをセット
  - 濁点・半濁点フラグが立っている場合、`0x68F5` にて基本文字の直上（`Y - 8` 等）へ濁点（`0xC0`）または半濁点（`0xC1`）のフォントを重ねて描画します（ウィンドウ境界外のときは `0x6921` 処理でクリッピングされます）。

### 3. メッセージ制御コード（MAIN.COM: 0x69F8 - 0x6B32）

`0x6726` の文字列描画ループでは、`0x48` 未満のバイト値を `0x69F8` の制御コード処理へ渡します。

- `0x00`: 文字列終端
- `0x01`: 改行（カーソルY座標を2進め、Xを先頭へ戻す）
- `0x02`: キャラクタ名展開（`0xC002` - `0xC005` の4文字を表示）
- `0x03`: アイテム名展開（直後1 ByteのアイテムIDを `0x3900` 以降のテーブルから取得して表示）
- `0x04`: 数値展開（テーブル参照16bit値）
- `0x05`: ギル数値展開（`0xC254` - `0xC256` の24bit値を表示）
- `0x06`: ワールド／現在関連数値展開（`0xC23E` を基に `0x8300` 領域を参照）
- `0x10` - `0x13`: パーティメンバー0〜3のステータス／名前／装備／魔法データ展開（`0x6AE9` - `0x6B32`）
- `0x14`: 1行送り（`0x6DFC`）

### 4. MAIN.COM 内に埋め込まれたシステムメッセージ（0x5DB9 - 0x5DF7）

ディスク交換や書き込み禁止エラー時に表示されるメッセージは、`MAIN.COM` 内に上記文字コードで直接格納されています。

| RAMアドレス | MAIN.COMオフセット | 格納内容（デコード文字列）                 |
| :---------- | :----------------- | :----------------------------------------- |
| `0x5DB9`    | `0x1DB9`           | ドライブにゲームディスクをいれてください   |
| `0x5DCE`    | `0x1DCE`           | ドライブにユーザーディスクをいれてください |
| `0x5DE4`    | `0x1DE4`           | ライトプロテクトがかかっています           |

※曲名と使用ダンジョンの不一致について:  
公式サントラで「海底神殿」と題されている楽曲（FC BGM ID: 0x4E）は、ゲーム中のダンジョン「海底神殿」では流れず、ラストダンジョン「過去のカオスの神殿」で演奏されます。
逆に、ダンジョン「海底神殿」で流れるのは「カオスの神殿」（FC BGM ID: 0x4C）です。

#### マップ切り替え時のBGM選択処理（MAIN.COM: 0x450B - 0x45B9）

- **ワールドマップ（`0xC230 == 0`）**: 搭乗状態 `0xC237` に基づき、徒歩・カヌー（`0` / `2`）は `0x3F`（`THEME.BGM`）、船（`1`）は `0x44`（`FUNE.BGM`）、飛空艇（`3`）は飛行音SE `0x0D` を鳴らした上で `0x48`（`HIKO_SEN.BGM`）を読み込みます。
- **サブマップ（`0xC230 >= 1`）**: `MAIN.COM` のファイル内オフセット `0x057D` - `0x05B9`（RAM `0x457D` - `0x45B9`、全61 Byte）に配置されたテーブル `BGM_TBL[SMAP ID]` を参照して対応するBGMファイルIDを `0xD000` にロードします（下表「修正前」の値がこの領域に実在しています）。

## バトル・アイテム・成長データ・エフェクト画像

### BDATA.TBL の内容

ファミコン版の Bank 11 (Bank B) および Bank 12 (Bank C) のデータブロックが格納されています。

| BDATA.TBL オフセット |  サイズ  | FC ROM物理アドレス | NESファイルアドレス | 格納データ内容                                                 |
| :------------------- | :------: | :----------------: | :-----------------: | :------------------------------------------------------------- |
| 0x0000 - 0x013F      | 320 Byte | 0x30000 - 0x3013F  |  0x30010 - 0x3014F  | 武器データ（40個 × 8Byte）                                    |
| 0x0140 - 0x01DF      | 160 Byte | 0x30140 - 0x301DF  |  0x30150 - 0x301EF  | 防具データ（40個 × 4Byte）                                    |
| 0x197D - 0x1A12      | 150 Byte | 0x2CFFD - 0x2D092  |  0x2D00D - 0x2D0A2  | 必要経験値テーブル（50レベル × 3Byte）                        |
| 0x1A20 - 0x1C6B      | 588 Byte | 0x2D094 - 0x2D2DF  | 0x02D0A4 - 0x02D2EF | 各ジョブ成長テーブル（Lv2-50: 6ジョブ × 49エントリ × 2Byte） |
| 0x1C70 -             |    -     |         -          |          -          | バトル用スプライトデータ（攻撃・魔法エフェクト等）             |

- **武器データ (0x0000-)**
  - 1レコード 8 Byte の構造は以下の通りです（全40種すべてで `+0x02` のクリティカル率は `1` 以上に設定されており、素手時のみ `0` になります。なお、装備可能ジョブフラグは本テーブルではなく別テーブルで管理されています）。
    - `+0x00`: 命中率
    - `+0x01`: 攻撃力
    - `+0x02`: 命中時クリティカル率
    - `+0x03`: 未使用等
    - `+0x04`: 武器属性（炎・冷気など）
    - `+0x05`: 武器種族特効（ドラゴン・アンデッドなど）
    - `+0x06`: 武器のグラフィックID（`0x80` - `0xAC`）
    - `+0x07`: 武器の色・アニメーション番号（`0x20` - `0x2C`）
- **防具データ (0x0140-)**
  - 1レコード4Byte: 重量, 防御力, 耐性, 特殊効果
- **必要経験値テーブル (0x197D-)**
  - 1エントリ3Byte（24bit リトルエンディアン）
  - Lv1: `00 00 00` (0)
  - Lv2: `28 00 00` (40)
  - Lv3: `C4 00 00` (196)
  - Lv4: `23 02 00` (547)
- **成長テーブル (0x1A20-)**
  - 各ジョブ Lv2-50（49エントリ × 2Byte: ステータス上昇4bitフラグ, MP上昇4bitフラグ）
  - 戦士: `3A 00 3B 00 3D 00 3A 00 3B 00 3D 00 ...`
  - 赤魔術士 Lv.21 のMP成長フラグはFC日本版と同一の `0x30`（Lv5・Lv6 MP上昇）です（北米NES版のみ `0x31`）。
- **バトルエフェクト用スプライトデータ (0x1C70-)**
  - DSKファイルオフセット: `0x7A070`
  - 攻撃や魔法エフェクト等に使用されるスプライトデータ。
  - 1スプライトあたり40Byte（パターン32Byte＋ラインカラー8Byte）の標準スプライト形式で格納されている。
  - スプライトカラーテーブルのカラーコード 1 - 3 は、エフェクトに合わせて変更されてからVRAMに書き込まれます。（ファミコン版カラーパレット切り替えの疑似再現）
  - パターンの並びは**ファミコン版ROM**の `0x26800` （NESヘッダを入れると`0x26810`）にあるエフェクト画像と同じ並びです。

### ワールドマップバトル背景割り当てデータ (BATTLE.COM内)

ワールドマップ上のタイル（0x00-0x7F）ごとに、バトル突入時に使用する背景グラフィックIDを指定するテーブルです。
ファミコン版の Bank 00（PRG `0x03300` / NESファイル `0x03310` / CPU `$B300`）とバイト単位で一致します。

- 格納ファイル: `BATTLE.COM` (ファイルID: `0x08`)
- ファイル内オフセット: `0x000BAE` - `0x000C2D` (128 Byte)
- DSKファイルオフセット: `0x0193AE` (セクタ: `0x00C9`)

## セーブデータ（ユーザーディスク）

MSX版ファイナルファンタジーのセーブデータは、専用のユーザーディスク（DSKイメージ）に記録されます。
ファイルシステム（SayDos）のディレクトリエントリ管理外に配置されており、セクタ番号固定で読み書きが行われます。

- 格納セクタ: `0x000A` - `0x000B`（セクタ 10 - 11、計2セクタ ＝ 1,024Byte）
- DSKファイルオフセット: `0x001400` - `0x0017FF`
- ゲーム実行時アドレス: メインRAM `0xC000` - `0xC3FF`
- チェックサム・データ署名: 存在しません（ベリファイなし）。
- ユーザーディスク読み書き仕様（`MAIN.COM: 0x5C2A` / `0x5C79`）:
  - 読み込み・書き込みともに `0x5CA7` によりスロット番号ワーク `0x5CEB` を `0x00` に設定し、セクタ番号 `0x000A + (0x5CEB) * 4`（= `0x000A`）に対して2セクタ分の入出力を実行します。
  - 読み込み時（`0x5C4E`）に先頭3 Byte（`0xC000` - `0xC002`）が文字列 `"NEW"`（`0x4E, 0x45, 0x57`）と一致する場合、未セーブ状態の初期ユーザーディスクと判定して Carry フラグをセットしてエラー扱いとします。

### ファミコン版セーブデータとの主な仕様差

1. **エンディアンの違い**
   - 経験値（3Byte）および所持金（3Byte）は、ファミコン版ではリトルエンディアンで格納されますが、MSX版ではビッグエンディアンで格納されます。
   - 最大HP・現在HP（各2Byte）は、両機種ともにリトルエンディアンです。
2. **座標管理の違い**
   - 乗り物（船・飛空艇）の座標は、ファミコン版が絶対タイル座標（`0-255`）であるのに対し、MSX版は画面中心表示用のカメラ原点タイル座標（絶対座標から `X - 7`, `Y - 6`）で保持されます。また格納順もファミコン版の `[X, Y]` に対し、MSX版は `[Y, X]` の順となります。
   - プレイヤー座標は、VRAMプレーン管理の都合上、32タイル単位のブロック番号（`0-7`）とブロック内オフセット（`0-31`）に上位・下位分割されて格納されます（絶対座標: `ブロック * 32 + オフセット + 7` (X) / `+ 6` (Y)）。
   - なお、船または飛空艇に搭乗中の乗り物座標同期はエディタ（`ff1_editor.html`）保存時の内部仕様であり、実機ゲーム中では下船時や着陸時に現在地が確定・更新されます。
3. **運河フラグの論理反転**
   - ファミコン版の `0x040C` bit 0 は「運河封鎖フラグ」であり、封鎖中に1、爆破開通時に0クリアされます。
   - MSX版の `0x16F2` bit 0 は「運河開通フラグ」であり、開通時に1がセットされます。
4. **全アイテム一元化ID体系**
   - ファミコン版では武器ID（1-40）と防具ID（1-40）が独立していますが、MSX版では全アイテムが一元化された通し番号で管理されます。

| 分類         | 項目数 | FC版 武器スロットID  | FC版 防具スロットID  | MSX版 一元管理ID |
| :----------- | :----: | :------------------- | :------------------- | :--------------- |
| なし (空き)  |   -    | `0`                  | `0`                  | `0`              |
| 重要アイテム |  21種  | - (範囲外参照: 87〜) | - (範囲外参照: 47〜) | `1` 〜 `21`      |
| 消費アイテム |  6種   | - (範囲外参照: 81〜) | - (範囲外参照: 41〜) | `22` 〜 `27`     |
| 武器         |  40種  | `1` 〜 `40`          | -                    | `28` 〜 `67`     |
| 防具         |  40種  | - (範囲外参照: 41〜) | `1` 〜 `40`          | `68` 〜 `107`    |

5. **魔法ID体系の違い**
   - ファミコン版は各レベルごとに独立した1-8の番号で管理されます。
   - MSX版は全レベル通しのID体系となっており、`0xB0 + (Lv - 1) * 8 + (魔法番号 - 1)`（`0xB0`-`0xEF`）が格納されます。
6. **レベル値の起算方法**
   - ファミコン版の内部値は `0` 起算（`0` = Lv1）。
   - MSX版の内部値は `1` 起算（`1` = Lv1、画面表示値と同一）。
7. **素パラメータ領域（`+0x28` - `+0x2A`）と能力値再計算の違い**
   - **ファミコン版**: `+0x28` - `+0x2A` に相当する領域は未使用です。武器画面終了時（Bank 0E `0xEEFE` 周辺）は、通常ジョブは外した武器と着けた武器の差分更新のみを行い、モンク／スーパーモンクのみ攻撃力を再計算します。防具画面終了時は防御力の合計値を再計算し、回避率は毎回 `48 + すばやさ (+0x11) - 装備防具の合計重さ` で再計算します。レベルアップ時（Bank 0B）は力が偶数になるたびに攻撃力 `+1`、素早さ上昇ごとに回避率 `+1`、ジョブ別成長値を命中率へ直接加算します。
   - **MSX2版**: `+0x28`（素の攻撃力）、`+0x29`（素の命中率）、`+0x2A`（素の回避率）に基礎値を独立して保持します。`MENU.COM`（`0x8D1F`）で装備画面を閉じた際は、必ず `+0x28` - `+0x2A` を基準に `+0x20` - `+0x23` を再計算し、`BATTLE.COM` のレベルアップ時（`0x8768`, `0x878B`, `0x87ED`）には `+0x28` - `+0x2A` と `+0x20` - `+0x23` の双方を更新します（外部からセーブデータを編集する際も、これらの領域を更新しないと装備画面開閉時に値が戻ります）。
   - **モンクの命中率・回避率計算について**: ファミコン版・MSX2版ともに、モンク専用の命中率・回避率計算式は存在せず全ジョブ共通です（回避率は `48 + すばやさ - 防具合計重さ`、命中率は `素の命中率 + 武器命中率`、モンク／スーパーモンクの命中率成長値は毎レベル `+3`）。モンク固有の処理は「攻撃力」「防御力」「攻撃回数（ヒット数2倍）」「クリティカル率」の4点のみです。

## ワークエリア

MSX版ファイナルファンタジーの `MAIN.COM`、`BATTLE.COM` の逆アセンブルリストおよび関連資料から、**ゲーム中で使用されているワークエリア（RAM領域）**を調査・解析し、機能別に分類して整理しました。

### 1. 最重要：`0xBD00` - `0xBFFF` の実態（MAIN.COMのサウンドワーク）

`ff1_msx_bugfix_btl.md` で「パッチコードが浸食してしまっている」と指摘されていた `0xBD00` 以降は、**`MAIN.COM` 内に組み込まれているBGM／効果音シーケンス演奏ドライバのワークエリア**です。

`MAIN.COM` の `.X752F` にて、開始時に `0xBD00` - `0xBF59`（計602Byte）が丸ごと 0 クリアされ、各チャンネルのトラッカー情報やPSGレジスタ反映バッファとして常時アクセスされています。

### 7. MAIN.COM の所持金・エンカウント・乱数処理

- **所持金加算と上限クリップ（`0x4FB8` - `0x5003`）**:
  - `0xC254` - `0xC256`（24bit ビッグエンディアン）に対する加算を行い、`999,999` ギル（`0x0F423F`）を超えた場合は `0x0F423F` に丸めます。
- **エンカウント判定とテーブル読み込み（`0x436E` - `0x43EE`）**:
  - ワールドマップ（`0xC230 == 0`）ではプレイヤーのブロック座標 `0xC231`（X）、`0xC233`（Y）および海上判定から `ENCOUNT.TBL`（ID: `0xD6`、RAM `0x0100` ロード）内のインデックスを算出します。
  - 内部確率テーブル（`0x4426`）と擬似乱数生成ルーチン（`0x5085`）で8スロットから敵編成IDを選択し、`BATSCENE.TBL`（ID: `0xD7`、RAM `0x0500` ロード）の対応レコード（16 Byte）を `0xDC32` - `0xDC41` へコピーし、敵編成IDを `0xDC31` へ格納してから `BATTLE.COM` を起動します。
- **擬似乱数生成（`0x5085` - `0x50BE`）**:
  - 内部ポインタ（`0x50BB`、`0x50BD`）でメモリ領域を走査し、取得値をもとに乱数値を更新・スケーリング（`0x505F`）します。

## BATTLE.COM の主要処理と既知の不具合

### 1. 戦闘バッファ初期化とモンク素手処理（`0x919D`, `0x91FA` - `0x9245`, `0x95D7`）

- **武器属性・特効のコピー漏れ（`0x91FA` - `0x920B`）**:
  - 戦闘開始時の味方戦闘バッファ（`IY = 0x3400` 以降）構築処理において、本来ダメージ計算側が参照するはずの `IY+0x43`（武器属性：`BDATA.TBL +0x04`）および `IY+0x44`（武器特効：`BDATA.TBL +0x05`）へのコピーが実装されておらず、代わりに武器の見た目データである `+0x06`（グラフィックID）と `+0x07`（色・アニメ番号）が `IY+0x46` と `IY+0x47` へコピーされています（`0xA514` 周辺の武器描画で参照）。その結果、`IY+0x43` と `IY+0x44` は常に `0x00` となります。
- **モンク素手処理のポインタ誤記バグ（`0x921E` - `0x9245`）**:
  - 戦闘開始時キャラバッファ作成処理（`0x919D`）から呼ばれる `0x921E` - `0x9245` には、ジョブIDがモンク（`0x02`）またはスーパーモンク（`0x08`）の場合に、素手用グラフィック（`IY+0x46 = 0xAC`）・色/アニメ（`IY+0x47 = 0x28`）、クリティカル率（`IY+0x45 = Lv * 2`）、ヒット数 2 倍（`IY+0x42 = ヒット数 * 2`）を設定する処理が実装されています。

```asm
; BATTLE.COM 0x921E - 0x9245
; 入力: IX = キャラクタデータ (0xC000〜), IY = 戦闘バッファ (0x3400〜)
921E: DD 7E 00     LD   A, (IX+00H)  ; ジョブID取得
9221: FE 02        CP   02H          ; モンクか
9223: 28 03        JR   Z, 9228H
9225: FE 08        CP   08H          ; スーパーモンクか
9227: C0           RET  NZ
9228: DD 7E 46     LD   A, (IX+46H)  ; バグ: 本来は FD 7E 46 (IY+46H) の誤記
922B: B7           OR   A
922C: C0           RET  NZ           ; 武器ありならリターン
922D: FD 36 46 AC  LD   (IY+46H), ACH ; 素手グラフィック設定
9231: FD 36 47 28  LD   (IY+47H), 28H ; 素手アニメ・色設定
9235: DD 7E 26     LD   A, (IX+26H)  ; レベル取得
9238: CB 27        SLA  A            ; レベル * 2
923A: FD 77 45     LD   (IY+45H), A  ; クリティカル率 = レベル * 2
923D: FD 7E 42     LD   A, (IY+42H)  ; ヒット数取得
9240: CB 27        SLA  A            ; ヒット数 * 2
9242: FD 77 42     LD   (IY+42H), A  ; ヒット数 = ヒット数 * 2
9245: C9           RET
```

  - `0x9228` で戦闘バッファの `IY+0x46` ではなくパーティデータの `IX+0x46` を参照してしまっています。`IX` は 1 人 64 Byte（`0x40`）単位の `0xC000` 以降を指しているため、1〜3人目は次キャラの名前5文字目（非ゼロ値）を読んで素手でも発動せず、4人目のみ後続領域の `0xC106`（`0x00` になりやすい領域）を読んで武器装備時でも発動する不具合が起きています。
- **最大ヒット数上限（`0x95D7`）**:
  - MSX2 版のダメージ計算処理では、1回の最大ヒット数の上限が 9 回に設定されています（ファミコン版は最大 16 回）。

### 2. レベルアップ処理（`0x867B` 周辺）と未呼出ルーチン群（`0x88EF` - `0x8A14`）

- **未呼出の能力値再計算ルーチン群（`0x88EF` - `0x8A14`, 計 294 Byte）**:
  - `BATTLE.COM` 内には攻撃力（`0x8914`）、命中率（`0x8932`）、防御力（`0x8950`）、回避率（`0x896B`）、属性耐性（`0x898F`）を再計算するルーチン群が配置されていますが、`BATTLE.COM` 内のどこからも呼び出されていないデッドコードとなっています。
  - 実際のレベルアップ処理（`0x867B`）では、力・素早さ上昇時に `(IX+0x20)` / `(IX+0x28)`（`0x8768`）や `(IX+0x23)` / `(IX+0x2A)`（`0x878B`, `0x8799`）を直接加算して更新します（防御力 `(IX+0x22)` は変更しません）。
- **命中率成長処理（`0x87ED` - `0x881B`）**:
  - 対象は `(IX+0x29)`（素の命中率）および `(IX+0x21)`（合計命中率）です。
  - 成長テーブル `0x8810` は `03 02 03 02 01 01  03 02 03 02 01 01`（戦士3、シーフ2、モンク3、赤2、白1、黒1、クラスチェンジ前後同値）となっており、ファミコン版と同一の値です。なお `0x87F8` には `CP 0x04` による上限判定があります。
- **魔法防御（MDEF）成長処理とジョブID加算バグ（`0x881C` - `0x8840`）**:
  - 対象は `(IX+0x25)`（魔法防御）です。成長テーブル `0x8835` は `03 02 04 02 02 02  03 02 04 02 02 02`（戦士3、シーフ2、モンク4、赤2、白2、黒2）であり、スーパーモンクは +4 に変更されていますが、戦士3・魔導士2 の設定が残っています（`CP 0x04` 上限チェックは存在しません）。
  - さらに、直前の加算処理に以下のバグが存在します。

```asm
881C: DD 7E 00    LD   A, (IX+00H)  ; A = ジョブID (0〜11)
...
8822: 21 35 88    LD   HL, 8835H    ; 魔法防御成長テーブル
8825: 19          ADD  HL, DE
8826: 46          LD   B, (HL)      ; B = テーブル値 (成長値)
8827: DD 86 25    ADD  A, (IX+25H)  ; バグ: A にジョブIDが残ったまま魔法防御を加算
882A: 80          ADD  A, B         ; 毎レベル「ジョブID + テーブル値」が加算される
```
