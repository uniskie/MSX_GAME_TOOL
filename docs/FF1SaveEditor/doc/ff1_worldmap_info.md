# ファミコン版『ファイナルファンタジー（FF1）』ワールドマップデータ構成リファレンス

ファミコン版FF1のワールドマップは、**256 × 256 タイル**（1タイル＝16×16ピクセル）のサイズで構成されています。ROMバイナリからデータを読み込み、画面上へ復元するまでの内部構造と処理手順は以下の通りです。

---

## 📄 参考ソースファイル情報 (FFHacksterEx)
本リファレンスは、**FFHacksterEx (v0.9.8.2-beta)** の以下の実装コードおよび設定定義ファイルをベースに構成されています。
*   **メインロジック（マップ伸長・タイル合成処理等）**: `src/libs/ff1-editors/OverworldMap.cpp`
*   **クラス定義・メンバ変数**: `src/libs/ff1-editors/OverworldMap.h`
*   **旧仕様（オリジナル版互換）ロジック**: `src/libs/ff1-editors/OverworldMapOrig.cpp` / `.h`
*   **ROMアドレス・定義マスター**: `src/apps/FFHacksterEx/FFHacksterEx.values.template` （プログラム内では `cart->ValuesPath` が指すINIファイルとして読み込まれます）

> ⚠️ **アドレス表記に関する注意点**
> 本ドキュメントに記載されているアドレス値は、一般的なエミュレータ用ROM形式（.nesファイル）に含まれる**16バイトのiNESヘッダを除いた、純粋なPRG-ROMデータ基準（バイナリエディタ等での実オフセット）**で記述しています。
> 元データ（FFHacksterExの設定ファイル等）はiNESヘッダ（16バイト）を含んだファイル先頭基準値となっているため、そちらを参照する場合は各アドレスに `+0x10` して読み替えてください。また、512バイトのトレーナーデータが含まれるROMの場合は、その分オフセットがずれる点にご注意ください。

---

## 1. ワールドマップ配置データの伸長 (Decompress Map)

ワールドマップの配置データは、ROM内ではランレングス（RLE）圧縮により格納されています。

### 📌 関連定義名（`FFHacksterEx.values.template` 設定値）
*   **`[OVERWORLDMAP_OFFSET]`** (値: `0x4000`): 行ごとのポインタテーブル開始位置（256行分、計512バイト）
*   **`[OVERWORLDMAP_PTRADD]`** (値: `-0x3FF0`): アドレス計算用の補正値（ヘッダ込みファイルオフセット算出用。純粋PRG基準では `-0x4000`）
*   **`[OVERWORLDMAP_START]`** (値: `0x4200`): 圧縮データの実体開始位置
*   **`[OVERWORLDMAP_END]`** (値: `0x7F40`): 圧縮データの実体終了位置

### 🛠 伸長アルゴリズム (`COverworldMap::DecompressMap`)
1.  行インデックス `Y = 0` から `255` までループ処理を行います。
2.  `OVERWORLDMAP_OFFSET + (Y * 2)` から2バイト（リトルエンディアン）を読み込み、対象行のCPUポインタアドレス（$8000〜）を取得します。
3.  ROM内の実オフセットを `ポインタ + OVERWORLDMAP_PTRADD` により算出します。
4.  そのアドレスから、**X座標が256に達するまで**以下の規則で1バイトずつ復号し、256×256の配列（`DecompressedMap[Y][X]`）へ格納します：
    *   **読み込んだ値（`temp`）が `0x80` 未満の場合**:
        *   単独のタイルです。その座標に `temp` を書き込み、`X` を 1 進めます。
    *   **`temp == 0xFF` の場合**:
        *   行末終端マーカーです。現在の `X` から `255` までの残りをすべて `0x00`（海）で埋めて、次の行（次の `Y`）へ移行します。
    *   **`temp` が `0x80` 以上の場合**:
        *   連続データです。タイル番号は `temp - 0x80`（`temp & 0x7F`）となります。
        *   続く1バイトを読み出して連続回数 `run` とします（※`run == 0` の場合は256回連続として扱います）。
        *   当該タイル番号を `run` 回数分だけ連続してマップ配列へ書き込み、`X` をその分進めます。

---

## 2. タイルの構成 (Tile Map Table)

伸長されたマップ配列の各数値（0〜127）は「タイル番号」です。1つのタイル（16×16ピクセル）は、ファミコンの最小描画単位である8×8ピクセルのCHRキャラクタ4つを組み合わせて構成されます。

### 📌 関連定義名
*   **`[OVERWORLDPATTERNTABLE_ASSIGNMENT]`** (値: `0x100`): タイルに対するCHRキャラクタ割り当てテーブル開始位置（512バイト）

### 🛠 タイルの組み立て (`COverworldMap::ReloadGraphics`)
タイル番号（`imagecount`: 0〜127）に対し、`offset = OVERWORLDPATTERNTABLE_ASSIGNMENT + imagecount` を基準として、128バイトプレーン構造から4象限のCHRキャラクタ番号を取得します：

*   **左上キャラクタ (UL)**: `cart->ROM[offset]`
*   **右上キャラクタ (UR)**: `cart->ROM[offset + 128]`
*   **左下キャラクタ (LL)**: `cart->ROM[offset + 256]`
*   **右下キャラクタ (LR)**: `cart->ROM[offset + 384]`

---

## 3. キャラクタパターンデータ (CHR Data)

上記で取得したキャラクタ番号に対応する、ドットグラフィック（波形・形状データ）の実体が格納されている領域です。

### 📌 関連定義名
*   **`[OVERWORLDPATTERNTABLE_OFFSET]`** (値: `0x8000`): ワールドマップ用CHRグラフィックデータの開始位置
*   **`cart->m_overworldtiles`**: 読み込んだグラフィックを保持するアプリ内部の `CImageList` 変数

### 🛠 データの取り出し
各8×8キャラクタは、ファミコン標準の **2bpp（4色カラー）形式（1キャラクタあたり16バイト）** で格納されています。
*   キャラクタ番号 `N` のグラフィックデータ開始位置は、`OVERWORLDPATTERNTABLE_OFFSET + (N * 16)`（または `N << 4`）で計算されます。

---

## 4. パレットデータの構成と適用 (Palette Assignment)

グラフィックに色情報を乗せるための定義です。ワールドマップ全体で共通のパレットデータを使用します。

### 📌 関連定義名
*   **`[OVERWORLDPALETTE_OFFSET]`** (値: `0x380`): ワールドマップ用パレットデータ本体（32バイト）の開始位置
*   **`[OVERWORLDPALETTE_ASSIGNMENT]`** (値: `0x300`): 各タイルが使用するパレットセット番号を定義するテーブル開始位置（128バイト）
*   **`[TRANSPARENTCOLOR]`** (値: `0xFF00FF` / マゼンタ): エディタ内部で透過色として定義されているRGBカラー

### 🛠 パレットの適用ルール (`COverworldMap::ReloadGraphics`)
1.  パレットデータ本体（32バイト分: BG 4色×4セット、SP 4色×4セット）を読み込みます。
2.  各タイル（`imagecount`）が使用するパレットセット番号（0〜3）を以下の計算で抽出します：
    *   `usepalette = (cart->ROM[OVERWORLDPALETTE_ASSIGNMENT + imagecount] & 3) << 2;`
3.  求まった `usepalette`（0, 4, 8, 12）をオフセットとして、4色1セットの色情報をそのタイルのキャラクタ描画に適用します。
    *   ※ファミコンPPUの背景共通色仕様（$3F00）に合わせるため、各パレットセットの先頭（色番号0）は、`OVERWORLDPALETTE_OFFSET + 0x10`（スプライトパレット先頭の共通背景色）で置き換えて描画されます。

---

## 5. その他のワールドマップ関連設定・定義

エディタの各種機能（初期座標やエンカウント率等）を制御する、 `FFHacksterEx.values.template` 内の設定定義です。

### ⚔ エンカウント・出現地域設定
*   **`[OWBATTLERATE_LAND_OFFSET]`** (値: `0x3C4FE`): 地上（歩行・カヌー）でのエンカウント確率（x/255）
*   **`[OWBATTLERATE_SEA_OFFSET]`** (値: `0x3C506`): 海上（船）でのエンカウント確率（x/255）
*   **`[BATTLEDOMAIN_OFFSET]`** (値: `0x2C000`): マップ上の敵出現地域（ドメイン）割り当てテーブル開始位置
*   **`[BATTLEPROBABILITY_OFFSET]`** (値: `0x3C58C`): 敵編成の出現確率（重み付け）テーブル開始位置

### 🗺 プレイヤー・乗り物の初期配置座標（X, Yの各1バイト構成）
*   **`[COORD_STARTING_OFFSET]`** (値: `0x3010`): ゲーム開始時の光の戦士の初期位置（X, Y）
*   **`[COORD_SHIP_OFFSET]`** (値: `0x3001`): 船の初期配置座標
*   **`[COORD_AIRSHIP_OFFSET]`** (値: `0x3005`): 飛空艇の初期配置座標
*   **`[COORD_BRIDGE_OFFSET]`** (値: `0x3009`): コーネリアの橋の架橋イベント座標
*   **`[COORD_CANAL_OFFSET]`** (値: `0x300D`): 運河（ニトロの火薬開通イベント）の座標

# ファミコン版『ファイナルファンタジーI』データ構造解析：プレーン（PLANE）形式採用の技術的背景

ファミコン版FF1のワールドマップにおける各種テーブル（タイルのキャラクタ割り当てなど）は、構造体の配列（インターリーブ形式）ではなく、フラットな128バイトごとの平面領域に分離された**「プレーン（PLANE）形式」**で格納されています。

乗算命令を持たないファミコンのCPU（6502 / 1.79MHz）において、1フレーム（1/60秒）の限られたVBLANK期間内にスクロール処理とネームテーブル転送を完結させるために設計された、合理的な技術的意図は以下の通りです。

---

## 1. 256×256座標からの1バイト直接アドレッシング
アセンブリ言語（6502）で広大な2次元マップ上の特定座標へアクセスする際、データ構造が複雑化しているとアドレス計算にクロック数を浪費します。

### 🛠 プレーン形式による処理の最小化
データを水平プレーンとして配置することで、CPUは以下の最小ステップで目的のタイル番号を特定できます：
*   **計算ロジック**: `行ポインタから取得したベースアドレス + X座標`
*   **ハードウェア命令との親和性**: 6502の「インデックス修飾絶対アドレッシング」（例: `LDA BaseAddress, X`）を直接適用できるため、乗算やシフト命令を一切挟まず、数クロックでマップからタイル番号を読み出せます。

---

## 2. 乗算を排除したタイルの合成（4x4キャラクタの抽出）
タイルの構成テーブル（`[OVERWORLDPATTERNTABLE_ASSIGNMENT]`）は、1つのタイル（16×16px）を構成する4つの8×8キャラクタ（左上・右上・左下・右下）の番号が、128バイトずつのプレーンに完全に分離して配置されています。

### 構造体形式との比較
もし `Tile { uint8_t ul, ur, ll, lr };` のような4バイト構造体の配列にした場合、タイル番号 `N` のデータを取得するために「`N × 4`」という乗算処理（シフト命令の多段実行）が毎アクセス発生します。

### 🛠 プレーン形式による処理の最小化
128バイトごとの固定長プレーンに分割しておくことで、タイル番号 `N` に対して**固定オフセットの加算（または固定ポインタ参照）のみで各象限のキャラクタ番号を瞬時に取得**できます：
*   **左上キャラクタ (UL)**: `BaseAddress + N`
*   **右上キャラクタ (UR)**: `BaseAddress + N + 128`
*   **左下キャラクタ (LL)**: `BaseAddress + N + 256`
*   **右下キャラクタ (LR)**: `BaseAddress + N + 384`

画面端のスクロール発生時に複数のタイルを連続展開する際のCPU負荷が、これにより最小限に抑えられます。

---

## 3. VRAM（ネームテーブル）への転送パイプラインの最適化
ファミコンの背景画面（PPUネームテーブル）への書き込みは、画面水平方向へ連続してキャラクタ番号を転送する構造になっています。

### 🛠 プレーン形式による処理の最小化
「左上プレーン」「右上プレーン」がメモリ上で連続しているため、スクロールラインを生成する際、以下のような連続バッファ転送ループがそのまま実行できます：
1.  展開対象行の「左上キャラクタ列」を連続してバッファへ転送
2.  続いて「右上キャラクタ列」を連続してバッファへ転送

描画直前にデータを分解・並び替えるオーバーヘッドが完全に排除されており、PPUのVBLANK期間内に転送を間に合わせるための極めて合理的なメモリ配置設計となっています。
